## 〇、两种痛点的现状诊断

### 痛点 1：感觉加载速度慢

"加载慢"实际可能发生在**三个不同环节**，对策完全不同：

| 环节 | 现状事实 | 用户可感知表现 | 主要耗时来源 |
|---|---|---|---|
| A. 模块载入（打开 Foundry/刷新） | `main.js`(4555 行) + `voice-manager.js` + `tts-engine.js` 一次性解析；ready 里串行注册 socket/代理/测试套件/心跳监听 | 打开世界后短暂卡顿 | JS 体积 + 启动逻辑串行 |
| B. 引擎侧（本机 9881） | 启动加载模型 30~190s（已有热身预合成，首次朗读不冷启动）；多模型常驻池 | 引擎停机重启后首次朗读慢 | CUDA 模型加载/预热 |
| C. 第一次朗读/每句朗读 | 每句走 /tts 合成（长文本并行分桶已提速 2~4 倍）；缓存 16 条；预加载音频 | 从"发消息"到"出声"的间隔 | 合成等待（无流式） |

### 痛点 2：选填的朗读风格"没用"

`stylePrompt`（朗读提示词）现状（`styleKeywordParams`，main.js:108）：
- 只把关键词映射成三类参数：**语速**（0.9~1.12）、**切分**（cut0/cut2）、**句间停顿**（frag）——对"严肃/温柔"这类风格**几乎无可感知效果**（语速微调 ≠ 语气）。
- 配置 LLM 时走 `/llm/style` 翻译成 speed_factor/split，**结果同样是语速/断句**，不改变声线情绪。
- 根因：**GPT-SoVITS 的声线/情绪由参考音频决定**，文本侧提示词不改变声音情绪；这正是对照报告里"模型级真情感"差距的工程化体现。

## 二、加载优化修改流程（分 4 步，可独立取舍）

### 步骤 1：客户端"按需懒加载 + 启动瘦身"（低风险，先做）
**改动点**：
- `scripts/main.js` ready 阶段：把**重头启动任务**（测试套件安装、LLM 健康预探测、心跳/回执监听注册）改为 `requestIdleCallback`/`setTimeout` 分批执行，首屏先出发送框。
- 语音管理器：首次打开才渲染立绘库网格（40 缩略图），收起时卸载。
- 引擎 `GET /characters` 增加 `?light=1` 轻量模式（只返回名字+头像，不返回 40 张 sprites 列表），立绘库展开时才拉全量。
**验证**：F12 Performance 录制"打开世界 → ready"耗时对比；语音管理器首次打开帧数。
**回滚**：各改动独立小提交，行为异常即 revert。

### 步骤 2：引擎"常用角色预热 + 缓存扩大"（中风险，收益直接）
**改动点**（`server/fvtt_api.py`）：
- 启动时除当前角色外，**预热前 2~3 个最近使用角色**（模型池常驻已有，改为按"最近使用"排序预热）。
- 合成缓存 16 → 64 条，并**落盘持久化**（重启不丢，同文本秒回）。
- `/tts` 加 `X-Fvtt-Cache` 命中头（客户端可显示"缓存命中"）。
**验证**：重启引擎后依次切 3 个角色朗读，对比启动/切换延迟；同句重发观察缓存命中。
**回滚**：缓存大小/持久化是配置项，可关。

### 步骤 3：引擎"首包流式返回"（高风险，收益最大）
**改动点**（引擎 + 客户端）：
- 合成改为分块返回（GPT-SoVITS 逐句/逐段完成即回传，客户端边收边播），首字延迟从"整句合成完"降到"第一句完成"。
- 客户端 PlaybackQueue 支持"分段流式插入"。
**验证**：长句（>80 字）首声延迟对比。
**回滚**：引擎加开关 `stream:false` 回退整段返回，客户端兼容两种模式。
**备注**：这是成品（SillyTavern 类）感知最快的核心手段，但涉及引擎/客户端双端改造，风险最高。

### 步骤 4：Foundry 侧打包瘦身（低风险）
**改动点**：`module.json` 增加 `"esmodules"` 拆分 + `"languages"`/压缩（如有构建线）；去掉不必要的 `styles/main.css` 大段（按需）。
**验证**：刷新后 JS 传输体积对比。
**回滚**：拆分是纯打包层，恢复一个文件即可。

## 三、朗读风格优化修改流程（3 方向，选一或多）

### 方向 A：风格 → 情绪槽 / 参考音频映射（推荐，复用现有能力）
**做法**：`stylePrompt` 关键词先匹配**情绪槽标签**（如"严肃/威严"→ 已有"威严"槽音频），命中则用该槽参考音频合成（真实语气）；未命中再退化到现在的语速/断句。
**改动点**：`sayText` 风格处理（main.js:506 附近）加"风格→findEmotionSlot 匹配"分支；语音管理器"朗读提示词"输入框加占位提示。
**收益**：用户配了情绪槽的角色，风格立即"真有效"（参考音频驱动 = 模型级语气）。
**验证**：配 1 个"威严"槽，提示词填"更威严"朗读对比。
**回滚**：纯新增分支，不影响现状。

### 方向 B：风格 → DSP 情绪调制打通
**做法**：风格关键词归一为情绪枚举（复用 `detectEmotion` 词表），走既有 `EMOTION_FX`（变调/变速/增益）调制，让"严肃"= 降调降速、"激动"= 升调加速。
**改动点**：main.js 风格分支把 `styleKeywordParams` 结果并入 `overrides.emotion` 调制链。
**收益**：无情绪槽也能感知"严肃/激动"差异（物理近似，诚实标注）。
**验证**：AB 对比朗读。
**回滚**：删除并入分支。

### 方向 C：换指令驱动引擎（远期，改动大）
**做法**：对照 [CosyVoice instruct / ElevenLabs 标签](https://www.josejang.com/posts/ai/gpt-sovits/)为引擎加文本指令通道（"用愤怒的语气说…"），或接 CosyVoice。
**收益**：模型级真情感（消除"风格没用"根因）。
**代价**：新引擎集成、角色包/流程重构，属于下一阶段立项。

## 四、结论与待确认项

1. **加载慢先定位场景**（请确认）：打开世界卡 / 引擎重启后第一句慢 / 每句等待久？
2. **建议先做**：步骤 1（懒加载）+ 步骤 2（预热+缓存）——低中风险、感知明显；风格先做方向 A（复用情绪槽）——工程量小、效果真实。
3. 步骤 3 流式与方向 C 指令引擎属重活，单独排期。

> 本流程未实施任何改动；确认优先级后按步骤逐项落地。
